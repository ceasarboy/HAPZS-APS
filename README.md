# APS-HAP：基于约束优化的智能排产系统

> **"瓶颈决定产出，约束定义最优。"** —— 基于 TOC（约束理论）理念，用数学规划求解生产调度的 NP-Hard 问题。

## 项目愿景

制造业的排产调度，本质上是在**有限产能**与**无限需求**之间寻找最优解。传统 ERP 只能看到"缺什么"，却无法告诉你"先做什么"。

APS-HAP 的目标很简单：**给定产能约束和工艺关系约束，自动生成可执行的车间级排产计划**——精确到工序、精确到小时。

## 当前阶段：工艺约束排产（Phase 1）

```
✅ 已实现                          🚧 规划中（Phase 2+）
─────────────────────────────────────────────────────
产能约束（日产能/小时产能）          机时约束（设备级排程）
工艺关系约束（DAG 串并行模型）      人员工时约束（技能-人员匹配）
FS/SS/FF/SF 四种依赖类型           物料约束（齐套检查）
冻结窗口（已排产时段锁定）          模具/夹具约束
紧急插单（动态优先级响应）          供应链协同
生产均衡优化（时间维度峰值惩罚）     能耗约束
换线矩阵（产品切换成本）            多工厂协同
```

**核心能力**：我们目前解决的是**"在给定产能下，按工艺路线把任务排到时间槽上"**这个问题。这不是简单的甘特图拖拽，而是用约束规划求解器在数万维变量空间中搜索最优解。

### 工艺模型：DAG 串并行

真实产线的工艺路线不是简单的线性流程。以 SMT 电子制造为例：

```
                    ┌─→ AOI检测 ─┐
SMT贴片 → 回流焊 ──┤             ├─→ ICT → FCT ──┐
                    └─────────────┘                ├─→ 涂覆 → 组装 → 老化 → 包装
                    ┌─→ X-Ray ──┐                  │
                    └───────────┘──────────────────┘
```

- **串行工序**：前驱完成后才能开始后继（FS：Finish-to-Start）
- **并行工序**：同一层级的多道工序可同时执行（AOI/X-Ray 同步检测）
- **四种依赖类型**：FS（完成-开始）、SS（开始-开始）、FF（完成-完成）、SF（开始-完成）
- **等待时间**：涂覆后需等待 12 小时才能组装（化学反应固化），支持"是否计入下班时间"

## 技术栈详解

### 求解引擎

| 引擎 | 类型 | 优势 | 劣势 |
|------|------|------|------|
| **OR-Tools CP-SAT** | 约束规划 | 最优解保证（OPTIMAL）；大规模问题稳定（500+ tasks/30s）；线性约束表达力强 | 单线程求解，无法利用多核；内存占用随变量数指数增长；浮点目标需整数化 |
| **DEAP GA** | 遗传算法 | 可并行评估；灵活的适应度函数；天然支持非线性目标 | 只有可行解（FEASIBLE），无最优保证；种群规模敏感；早熟收敛风险 |

**选择策略**：生产环境用 CP-SAT 求精确解，GA 作为备选和对比基线。

### 后端

| 技术 | 版本 | 用途 | 优势 | 劣势 |
|------|------|------|------|------|
| **FastAPI** | 0.111 | Web 框架 | 异步高性能；自动 OpenAPI 文档；类型安全 | 生态不如 Django 成熟 |
| **Pydantic V2** | 2.7 | 数据校验 | Rust 加速的验证引擎；JSON Schema 生成 | V1→V2 迁移有破坏性变更 |
| **httpx** | 0.27 | HTTP 客户端 | 原生 async；API 兼容 requests | 社区小于 requests |
| **Celery + Redis** | 5.4/5.0 | 异步任务队列 | 排产任务后台执行（30s+ 不阻塞 API） | 架构复杂度增加；需额外维护 Redis |

### 前端

| 技术 | 版本 | 用途 | 优势 | 劣势 |
|------|------|------|------|------|
| **React 18** | 18.3 | UI 框架 | 生态最大；Concurrent Mode；团队熟悉 | 状态管理碎片化 |
| **Ant Design 5** | 5.18 | 组件库 | 企业级组件齐全；CSS-in-JS 主题定制；中文友好 | 包体积大（tree-shaking 可缓解）；默认样式辨识度高 |

| 优势 | 劣势 |

## 核心数据模型

14 张 HAP 工作表，支撑工序级排产：

```
产品主数据 ──→ 产品工艺 ──→ 工序信息（10道工序）
                  │              │
                  │              ├─ 约束类型（机时/人员工时）
                  │              ├─ 等待时间 + 是否计入下班
                  │              └─ 准备时间
                  │
                  ├─ 工序顺序（seq，同seq=并行）
                  └─ 依赖类型（FS/SS/FF/SF）

产线 ──→ 产线工艺配置 ──→ 资源日历（小时级）
              │                │
              ├─ 日产能         └─ 7天×12时段×产线×工序
              ├─ 效率
              └─ 是否瓶颈

需求计划 ──→ 排产结果 ←── 换线矩阵
  │            │
  ├─ 优先级     ├─ 工序级任务
  └─ 交期       └─ 时间槽分配
```

## 排产求解流程

```
1. 从 HAP 拉取全量数据（产品/工艺/产线/日历/需求）
2. 构建虚拟工作中心：(产线, 工序) 对 → 13 个 VWC
3. 展开排产项：(需求, 工序) 对 → 551 个 EI
4. 构建约束模型：
   ├─ 产能约束：每时段每 VWC 的排产数量 ≤ 小时产能
   ├─ DAG 前驱约束：succ_cum(t) ≤ pred_cum(t-1)（按时间键对齐）
   ├─ 依赖类型延迟：FS=wait+prep+setup, SS/FF/SF 自动计算
   ├─ 冻结窗口：frozen_time_indices 跳过变量创建
   └─ 生产均衡：over_terms 惩罚超过阈值的时段负荷
5. CP-SAT 求解 → OPTIMAL/FEASIBLE
6. 解码结果 → 推送 HAP 排产结果表
```

## 快速开始

### 前置条件

- Python 3.11+
- Node.js 18+
- Redis（可选，用于 Celery 异步任务）
- 明道云 HAP 账号（用于主数据管理）

### 后端启动

```bash
cd backend
pip install -r requirements.txt

# 配置环境变量
cp .env.example .env
# 编辑 .env，填入 HAP 鉴权信息和 API_KEY

# 启动服务
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

### 前端启动

```bash
cd frontend
npm install
npm run dev
```

访问 http://localhost:3000

### Docker 部署

```bash
cd deploy
docker-compose up -d
```
