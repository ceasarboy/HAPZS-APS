# APS-HAP 融合调整方案

> 基于 OpenAPS 技术栈 + TOC/DBR 理论 + 遗传算法仿真优化，取长补短的整体方案

---

## 一、方案融合策略

### 1.1 各方案优劣势对比

| 方案 | 优势 | 劣势 | 取舍 |
|:---|:---|:---|:---|
| **OpenAPS + ortools** | 代码可运行、HAP 对接已通、CP-SAT 求解确定性强 | 无 DBR 逻辑、无缓冲管理、无批量策略、硬软规则未分层 | **保留基础设施，重构求解引擎** |
| **TOC/DBR 动态排产** | 理论成熟、混合方向策略科学、缓冲管理实用 | 纯理论无代码、依赖瓶颈识别准确度 | **吸收核心逻辑：DBR 方向 + 缓冲管理** |
| **GA + 仿真** | 大规模搜索能力强、软规则量化自然、What-if 天然支持 | 仿真引擎重、收敛不确定、开发量大 | **吸收思想：适应度函数 + What-if，算法待比较** |

### 1.2 融合原则

1. **基础设施复用**：React + FastAPI + HAP + Docker 的技术栈和已跑通的对接链路全部保留
2. **制造逻辑重构**：引入 DBR 混合方向、硬软规则分层、缓冲管理、批量策略
3. **算法开放竞争**：ortools CP-SAT / GA / 混合算法并行开发，用同一组测试用例对比，择优选用
4. **渐进式演进**：不推翻重来，在现有骨架上逐层叠加能力

### 2.2 与原架构的关键变化

| 变化点 | 原架构 | 调整后 |
|:---|:---|:---|
| 求解引擎 | 单一 ortools 直接求解 | **DBR 编排器 → 约束构建器 → 求解器适配层**（三层解耦） |
| 算法选择 | ortools 唯一 | **ortools / GA / 混合** 三种求解器可切换，统一接口 |
| 排产方向 | 无方向概念（时间槽分配） | **瓶颈顺排 + 前序倒排 + 后序推动**（DBR 混合方向） |
| 规则处理 | 全部混入约束 | **硬规则→约束条件，软规则→目标函数权重** |
| 批量策略 | 按订单整批 | **加工大批量 + 流转小批量 + 工序重叠** |
| 缓冲管理 | 无 | **时间缓冲 + 红黄绿三色监控** |
| 插单处理 | 无 | **What-if 模拟 + 冻结窗口 + 局部重排** |
| MES 反馈 | 无 | **预留 MES 回传接口，实际时间戳驱动重排** |

## 三、核心模块设计

### 3.1 DBR 编排器（新增核心模块）

**职责**：识别瓶颈、确定排产方向、计算缓冲、编排求解顺序

```
输入：订单池 + 工艺路径 + 资源日历 + 物料齐套状态
  │
  ├─ Step 1: 瓶颈识别
  │   计算各工作中心 L/C 比（负荷/产能）
  │   L/C > 95% → 标记为当前 Drum
  │   支持多瓶颈场景（主瓶颈 + 次瓶颈）
  │
  ├─ Step 2: 方向策略
  │   Drum 工序 → 有限产能顺排（Forward）
  │   Drum 前工序 → 逆推倒排（Backward），确定投料时间（Rope）
  │   Drum 后工序 → 节拍推动（Push），跟随 Drum 产出节奏
  │
  ├─ Step 3: 缓冲计算
  │   时间缓冲 = (平均前置时间 × 波动率系数) + MTTR
  │   物流缓冲 = 物理转移时间 + 波动余量（如 1h + 0.5h）
  │   工艺缓冲 = 固化/晾干等强制等待（非占用式）
  │
  ├─ Step 4: 批量策略
  │   加工批量 = 成组技术聚类后的合并量（减少换产）
  │   流转批量 = 独立设定（如 50 只/次），触发工序重叠
  │
  └─ Step 5: 输出求解任务
      将编排结果转化为约束构建器的输入
```

**关键数据结构**：

```python
@dataclass
class DBRPlan:
    drum_workcenter: str           # 瓶颈工作中心 ID
    drum_schedule: List[Task]      # 瓶颈顺排结果
    pre_drum_schedule: List[Task]  # 前序倒排结果
    post_drum_schedule: List[Task] # 后序推动结果
    buffers: Dict[str, Buffer]     # 各解耦点的缓冲配置
    rope_points: List[RopePoint]   # 投料控制点（绳子）
    batch_plan: BatchPlan          # 加工批量/流转批量方案

@dataclass
class Buffer:
    workcenter_id: str
    buffer_type: str               # time / inventory / transfer / curing
    duration_hours: float          # 缓冲时长
    green_zone: float              # 安全区阈值
    yellow_zone: float             # 警戒区阈值
    red_zone: float                # 危险区阈值

@dataclass
class BatchPlan:
    processing_batch: int          # 加工批量（大）
    transfer_batch: int            # 流转批量（小）
    overlap_enabled: bool          # 是否启用工序重叠
```

### 3.2 约束构建器（新增核心模块）

**职责**：将业务规则转化为求解器可识别的数学模型

#### 硬规则（约束条件，不可违反）

| 硬规则 | 数学表达 | 说明 |
|:---|:---|:---|
| **有限产能** | `Σ x[i,t,w] ≤ Capacity[w,t]` | 每个时间槽每条产线产量不超过产能 |
| **物料齐套** | `x[i,t,w] = 0 if material_not_ready[i,t]` | 物料未齐套不可排产 |
| **工艺顺序** | `start[i,k+1] ≥ end[i,k] + buffer[k]` | 工序间必须满足先后顺序 + 缓冲 |
| **资源兼容** | `x[i,t,w] = 0 if incompatible[i,w]` | 产品与产线不兼容不可排 |
| **技能矩阵** | `x[i,t,w] ≤ skill_match[i,w,t]` | 操作员技能不匹配不可排 |
| **冻结窗口** | `x[i,t,w] = fixed if t < freeze_horizon` | 已下发/已开工的计划不可变更 |
| **固化等待** | `start[i,k+1] ≥ end[i,k] + curing_time[k]` | 工艺强制等待不可压缩 |
| **物流转移** | `start[i,B] ≥ end[i,A] + transfer_time[A,B]` | 跨线转移时间不可省略 |

#### 软规则（目标函数，权重优化）

| 软规则 | 量化方式 | 默认权重 | 说明 |
|:---|:---|:---|:---|
| **交期达成 (OTD)** | `Σ max(0, completion[i] - due[i]) × priority[i]` | 0.35 | 延迟惩罚，高优先级权重更大 |
| **换产最小化** | `Σ changeover_time[i,j] × switch[i,j]` | 0.25 | 相邻产品换线时间惩罚 |
| **负荷均衡** | `max_w(line_total[w]) - min_w(line_total[w])` | 0.15 | 各产线产量偏差最小 |
| **WIP 控制** | `Σ wip_level[i,t]` | 0.10 | 在制品水平惩罚 |
| **瓶颈利用率** | `1 - drum_utilization` | 0.10 | 瓶颈资源利用率最大化 |
| **计划稳定性** | `Σ |new_plan[i] - old_plan[i]|` | 0.05 | 与上次计划偏差最小 |

**权重可配置**：不同场景（日常排产 / 紧急插单 / 月末冲刺）可切换权重方案。

### 3.3 求解器适配层（新增核心模块）

**职责**：统一求解器接口，支持多种算法可切换

```python
class BaseSolver(ABC):
    """求解器基类 - 所有求解器必须实现此接口"""

    @abstractmethod
    def solve(self, problem: SchedulingProblem) -> SolveResult:
        """输入统一的问题描述，输出统一的结果格式"""
        pass

    @abstractmethod
    def get_capabilities(self) -> SolverCapabilities:
        """声明求解器能力（支持哪些约束类型、求解规模上限等）"""
        pass

class SolveResult:
    status: str                    # OPTIMAL / FEASIBLE / INFEASIBLE / TIMEOUT
    tasks: List[ScheduledTask]     # 排产结果
    objective_values: Dict[str, float]  # 各目标函数值
    solve_time_seconds: float      # 求解耗时
    solver_name: str               # 求解器名称
    metadata: Dict                 # 求解器特有信息（如 GA 代数、ortools 分支数等）
```

#### 三种求解器对比（待实测验证）

| 维度 | ortools CP-SAT | 遗传算法 (GA) | 混合策略 |
|:---|:---|:---|:---|
| **原理** | 约束传播 + 分支定界 | 种群进化 + 交叉变异 | CP-SAT 求硬约束可行解 → GA 优化软规则 |
| **硬规则处理** | 天然强约束，100% 保证 | 需罚函数或修复算子，可能违反 | CP-SAT 保证硬约束 |
| **软规则优化** | 加权目标函数，单次求解 | 多代进化，全局搜索能力强 | GA 在可行域内搜索更优解 |
| **求解速度** | 小规模秒级，大规模分钟级 | 依赖种群大小和代数 | 两阶段，总耗时 = CP-SAT + GA |
| **解质量** | 可证明最优（若给够时间） | 近似最优，依赖参数调优 | 平衡可行性与最优性 |
| **What-if 支持** | 每次重新求解 | 种群可复用，增量进化快 | GA 种群复用 |
| **DBR 适配** | 需手动拆分方向 | 自然支持（编码为序列） | CP-SAT 做 Drum 排，GA 做全局优化 |
| **开发复杂度** | 低（ortools 成熟） | 中（需设计编码/交叉/变异） | 高（两套系统串联） |
| **适用场景** | 硬约束严格、规模可控 | 软规则复杂、搜索空间大 | 两者兼需 |

**结论**：不急于定论，三种求解器并行开发，用统一的基准测试用例对比后决定。

## 五、排产流程（调整后）

### 5.1 日常排产流程（每半天一次）

```
1. 数据同步
   HAP 拉取：订单 + 工艺路径 + 资源日历 + 物料齐套 + 换线矩阵
   ↓
2. 订单清洁（OCF）
   过滤无效需求 → 分段 BOM 齐套检查 → 产线兼容性锁定
   ↓
3. 瓶颈识别
   计算各工作中心 L/C 比 → 标记 Drum → 识别移动瓶颈
   ↓
4. DBR 编排
   Drum 顺排 → 前序倒排（Rope）→ 后序推动 → 缓冲嵌入 → 批量策略
   ↓
5. 约束构建
   硬规则 → 约束条件 | 软规则 → 目标函数权重
   ↓
6. 求解
   调用求解器（ortools / GA / 混合）→ 输出候选方案
   ↓
7. 评估
   硬规则校验 → 软规则评分 → KPI 计算 → 综合得分
   ↓
8. 方案对比（可选）
   生成 2~3 个方案 → A/B 对比 → 人工确认
   ↓
9. 发布
   选定方案 → 推送 HAP 排产结果表 → 更新订单状态
```

### 5.2 紧急插单流程

```
1. 插单触发
   新订单进入 → 标记 P1 优先级
   ↓
2. 冻结窗口
   已开工/已下发的任务冻结 → 仅调整冻结窗口外的计划
   ↓
3. What-if 模拟
   方案 A：插单排在最前，后续顺延
   方案 B：插单排在缓冲间隙
   方案 C：插单排在换线切换点
   ↓
4. 影响评估
   各方案对 OTD / 换线 / 均衡的影响量化
   缓冲区水位变化（是否进入红区）
   ↓
5. 人工决策
   展示影响对比 → 管理者选择方案 → 发布
```

## 六、算法对比测试方案

### 6.1 基准测试用例

| 用例 | 规模 | 特点 |
|:---|:---|:---|
| **T1 基础** | 10 项目 × 4 产线 × 12 时间槽 | 无换线约束，验证基本可行性 |
| **T2 换线** | 20 项目 × 4 产线 × 12 时间槽 | 含换线矩阵，验证软规则优化 |
| **T3 DBR** | 20 项目 × 4 产线 × 3 工序 | 含瓶颈识别 + 混合方向 + 缓冲 |
| **T4 批量** | 20 项目 × 4 产线 × 3 工序 | 含加工批量/流转批量/工序重叠 |
| **T5 插单** | T3 基础 + 3 个紧急插单 | 验证冻结窗口 + What-if |
| **T6 压力** | 50 项目 × 8 产线 × 24 时间槽 | 验证大规模性能 |

### 6.2 评估指标

| 指标 | 说明 | 权重 |
|:---|:---|:---|
| **硬规则违反数** | 必须为 0，否则不合格 | 一票否决 |
| **OTD 达成率** | 按时交付的订单比例 | 30% |
| **换线总时长** | 所有换线时间之和 | 20% |
| **瓶颈利用率** | Drum 工作中心的时间利用率 | 20% |
| **产线均衡率** | 1 - (max负荷 - min负荷) / max负荷 | 15% |
| **求解时间** | 从提交到出解的耗时 | 15% |

### 6.3 对比维度

| 维度 | 说明 |
|:---|:---|
| **解质量** | 6 个评估指标的加权得分 |
| **求解速度** | 各用例的求解时间 |
| **稳定性** | 同一用例运行 10 次的结果方差（GA 有随机性） |
| **可扩展性** | T6 压力用例的表现 |
| **开发成本** | 代码量、调试难度、维护成本 |

## 七、前端界面调整

### 7.1 新增页面

## 九、风险与应对

| 风险 | 等级 | 应对 |
|:---|:---|:---|
| DBR 瓶颈识别不准 | 高 | 支持人工指定瓶颈 + 自动识别双模式，初期以人工为主 |
| GA 收敛慢/不稳定 | 中 | Phase 0 先与 ortools 对比，若无明显优势则降级为辅助 |
| 工序重叠模型复杂度高 | 中 | 先实现单工序重叠，多工序重叠作为 P2 优化 |
| HAP 工作表调整影响现有数据 | 低 | 新增表不动旧表，旧表只加字段不改结构 |
| 求解性能不达标 | 低 | 20 项目 × 4 产线规模下，ortools 已验证秒级出解 |
